# Database Architecture

---

## Technology Stack

| Component | Technology |
|---|---|
| Database Engine | PostgreSQL 15+ |
| Async Driver | asyncpg |
| ORM | SQLAlchemy 2.x (async) |
| Migrations | Alembic |
| Connection Pooling | asyncpg pool via SQLAlchemy |

---

## Schema Strategy: Shared Schema with company_id Isolation

SMRITI uses a **single shared PostgreSQL schema** for all companies within a tenant.

Row-level isolation is enforced via:
1. `company_id` column on every business entity table
2. `TenantContext` injected into every service
3. Backend query filters: `WHERE company_id = :company_id`
4. Orchestrator-level ownership validation (e.g. customer-tenant check)

### Why Not Separate Schemas Per Company?

| Option | Decision |
|---|---|
| Separate DB per company | ❌ — operational overhead, hard to consolidate |
| Separate schema per company | ❌ — Alembic migration complexity |
| Shared schema + `company_id` | ✅ CHOSEN — single migration path, native consolidation |

## Base Model Pattern

Every business entity table inherits from `SMRITIBase`:

```python
class SMRITIBase(Base):
    __abstract__ = True
    id         = Column(String(50), primary_key=True)
    uuid       = Column(String(36), default=lambda: str(uuid4()), unique=True)
    tenant_id  = Column(String(50), nullable=True, index=True)
    company_id = Column(String(50), ForeignKey("companies.id"), index=True)
    branch_id  = Column(String(50), ForeignKey("branches.id"), nullable=True, index=True)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
    modified_at= Column(DateTime(timezone=True), onupdate=func.now(), server_default=func.now())
    created_by = Column(String(50), nullable=True)
    updated_by = Column(String(50), nullable=True)
    is_active  = Column(Boolean, default=True, nullable=False)
    is_deleted = Column(Boolean, default=False, nullable=False)
    deleted_at = Column(DateTime(timezone=True), nullable=True)
    deleted_by = Column(String(50), nullable=True)
    version    = Column(Integer, default=1, nullable=False)
```

**Critical:**
- `id` is a **string** (not integer auto-increment) — generated by the application or API
- `uuid` is for external exposure (immutable public identifier)
- Soft-delete via `is_deleted = True` — never hard-delete business records

## Primary Key Strategy

| Context | Format | Example |
|---|---|---|
| Company | `comp-{hex12}` | `comp-a1b2c3d4e5f6` |
| Branch | `br-{hex12}` | `br-a1b2c3d4e5f6` |
| Customer | `cust-{hex12}` | `cust-a1b2c3d4e5f6` |
| Invoice | `inv-{hex12}` | `inv-a1b2c3d4e5f6` |
| User | `usr-{hex12}` | `usr-a1b2c3d4e5f6` |
| Product | `prod-{hex12}` | `prod-a1b2c3d4e5f6` |

**Rule:** Application generates IDs — database does NOT use sequences for primary keys of business entities.

## Key Tables

| Table | Purpose |
|---|---|
| `companies` | Company master — legal entities |
| `branches` | Branch master — per company |
| `users` | User accounts (all companies) |
| `user_company_assignments` | User ↔ Company access matrix |
| `user_branch_assignments` | User ↔ Branch access (optional) |
| `customers` | Customer aggregate root |
| `suppliers` | Supplier aggregate root |
| `products` | Product/Item master |
| `sales_invoices` | Sales invoice header |
| `sales_invoice_items` | Invoice line items |
| `sales_invoice_payments` | Payment records |
| `purchase_orders` | Purchase order header |
| `stock_ledger` | Immutable inventory movement ledger |

---

## Triggers

| Trigger | Table | Purpose |
|---|---|---|
| `stock_ledger_trigger` | `stock_ledger` | Auto-updates `current_stock` on physical movements |
| `numbering_autonumber` | Various | Auto-generates document numbers (INV-00001, etc.) |

**Rule:** Triggers are READ-ONLY safe for concurrent sessions. Never design triggers that lock rows across company boundaries.

## Migration Governance

See [`06_DATABASE/MIGRATION_GOVERNANCE.md`](../06_DATABASE/MIGRATION_GOVERNANCE.md) for full rules.

Key rules:
- All migrations via Alembic
- Never drop columns in production — add `is_deleted` instead
- Migration scripts must be backward-compatible
- No data migrations in schema migration scripts
