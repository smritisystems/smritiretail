# ADR-0006: Stage 3B Registration Runtime and Stage 4 Event Service Freeze

## Status

Accepted and Frozen (2026-08-01) — authoritative SPK platform freeze record for Stage 3B registration and Stage 4 platform event service

## Context

SMRITI Platform Kernel must preserve a narrow, contract-driven runtime boundary for registration and event services without expanding into product-launch, entitlement, marketplace, broker-specific messaging, or startup-orchestration concerns. The runtime implementation now validates registration manifests, signatures, compatibility metadata, registration persistence, event envelopes, registry state, publisher/subscriber delivery, serializer round-trips, retry/dead-letter handling, and integration across the platform runtime. This ADR locks the governance boundary for that behavior.

## Decision

1. **Registration scope remains narrow**
   - Stage 3B covers registration manifest handling, validation, signature verification, compatibility validation, registration persistence, and status lifecycle.
   - Stage 3B does not implement launch, token issuance, entitlement evaluation, marketplace publication, or customer visibility.

2. **Platform event scope remains bounded**
   - Stage 4 covers event envelope handling, event registry lifecycle, publisher/subscriber delivery, serializer abstraction, validator behavior, retry/dead-letter handling, metrics, transport health, and memory-transport execution.
   - Stage 4 does not implement broker-specific messaging, cross-service orchestration, or notification-domain business logic.

3. **The runtime contract is canonical**
   - Registration state shall use the canonical lifecycle values:
     - Draft
     - Validated
     - Approved
     - Published
     - Deprecated
     - Retired
   - Event lifecycle values shall use the canonical platform states:
     - Register
     - Validate
     - Publishable
     - Deprecated
     - Retired
   - These lifecycle values shall be represented by shared runtime definitions rather than ad hoc strings.

4. **Compatibility policy remains version-based**
   - Compatibility validation must verify constitution, SPC, SDK, and design-system compatibility metadata using the platform baseline.
   - The registration runtime must reject incompatible manifests before storing them as registered.
   - Event definitions must remain compatibility-aware and reject structurally incompatible versions.

5. **Signature and envelope policies remain deterministic**
   - Registration signatures must be computed from a canonical payload and compared against the stored signature value.
   - Event envelopes must remain immutable, schema-versioned, tenant-aware, correlation-aware, and serializer-round-trippable.
   - Any tampered, missing, or mismatched signature or invalid event envelope must fail the platform runtime path.

6. **Stage 4 is frozen as a platform baseline**
   - The Stage 4 platform event service is now considered frozen for the current runtime baseline.
   - No new event-service features should be introduced without a new ADR and architecture review.
   - Only bug fixes, security fixes, and performance improvements are permitted to the frozen runtime surface.

## Consequences

### Positive
- Preserves a clean Stage 3B and Stage 4 boundary that matches the platform constitution.
- Ensures registration and event behavior are auditable, testable, and compatible with the broader freeze-and-evidence workflow.
- Keeps runtime implementation aligned with governance, deferred-scope controls, and platform stability expectations.
- Establishes a stable foundation for Stage 5 notification services and future platform services.

### Trade-offs
- Registration and event services are intentionally limited and will not absorb orchestration, broker-specific messaging, or product-launch concerns.
- Future lifecycle transitions, transport adapters, and advanced routing capabilities should be introduced as separate milestones or ADRs.

## Deferred Work

The following domains remain explicitly deferred beyond Stage 4:
- notification delivery orchestration and business workflows
- configuration management
- audit workflow
- telemetry integration
- public API gateway behavior
- broker-specific transport implementations
