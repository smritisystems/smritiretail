## 2. Section A -- Identity Code Semantics

### A.1 What identity_code Actually Is

ARCH-CRM-001 described identity_code as a 'cross-company deduplication anchor' comparable
to a PAN or canonical business key. **This characterisation is INCORRECT.**

**Evidence (VERIFIED FROM SMRITI SOURCE CODE):**

```python
# code_generator.py (IdentityEngine internal)
identity_code = f"{actual_prefix}-{allocated_seq:0{padding}d}"
# For customers: CRM-CUS-00000001, CRM-CUS-00000002, ...
```

```python
# Migration v1464 -- Unified Identity Control Plane
{"identity_code_prefix": "CRM-CUS"}  # registered prefix for Customer entity
```

```python
# test_identity_engine.py -- verified assertions
assert code1 == "CRM-CUS-00000001"
assert code2 == "CRM-CUS-00000002"
```

**identity_code is a GOVERNED SEQUENTIAL SYSTEM IDENTIFIER.** It is:
- Machine-generated by IdentityEngine (never user-assigned or business-derived).
- Format: CRM-CUS-{8-digit sequence}.
- Globally unique across the tenant (UNIQUE constraint, no company_id scope).
- NOT a business identity anchor (not PAN, not GSTIN, not mobile-derived).
- Used for cross-document resolution via MasterResolver (Tier 1 resolution).
- Used in adapters (customer_adapter.py) to look up customers during bulk import.

### A.2 Trace of Reads and Writes

**WRITES:**

| File | Operation | Trigger |
|---|---|---|
| engine.py (IdentityEngine.allocate_internal) | identity_code = CRM-CUS-NNNNNNNN generated atomically | Customer create via service |
| customer_adapter.py:448 | identity_code=id_code | Flat-file/bulk import adapter |
| univ_party_svc.py:116 | identity_code=identity_code | Universal party service create |

**READS:**

| File | Line | Operation |
|---|---|---|
| customer_adapter.py | 207 | Customer.identity_code == identity_code -- dedup during import |
| resolver.py | 139, 202, 239 | MasterResolver Tier 1 resolution |
| crm.py (CRM API) | N/A | NOT queried in /crm/customers/search or list endpoints |

**CRITICAL FINDING:** The CRM CRUD API does not search by identity_code.
identity_code is NOT exposed in customer search/list API responses currently.

### A.3 Null Handling

**Live DB evidence (VERIFIED FROM LIVE DATABASE, smriti001, 2026-10-19):**
```
total_customers:      879
with_identity_code:   690  (78.5%)
null_identity_code:   189  (21.5%)
duplicate codes:        0  (UNIQUE constraint enforced)
```

189 NULL rows = customers created before IdentityEngine integration (pre-v1397 migration).
These customers lack a canonical system identifier. This is NOT a blocker for Model C
but means 21.5% of customers cannot be resolved by identity_code.

### A.4 Canonical Business Anchor Recommendation

**identity_code CANNOT serve as the canonical business anchor** because:
1. It is machine-generated, not derived from PAN/GSTIN/mobile.
2. 189 customers (21.5%) have NULL identity_code.
3. It is not exposed to users in the search or list API.
4. Two rows for the same business entity (e.g. cust-rrl-192b561d and cust-ril-1888)
   would have DIFFERENT identity_codes -- defeating its use as a merger key.

**Recommended canonical business anchor:**
- B2B corporate customers: pan_number (already on customers, nullable varchar(10))
- Retail consumers: mobile number (practical, widely available)
- Composite deduplication key: (pan_number OR mobile OR gstin) within tenant

**ARCH-CRM-001 backfill SQL is INCORRECT and will fail:**
```sql
-- INCORRECT (credit_limit, credit_days not on customers table):
SELECT id, company_id, branch_id, customer_group_id, credit_limit, credit_days, status FROM customers

-- CORRECT backfill (credit comes from customer_groups):
INSERT INTO customer_company_relationships
  (id, customer_id, company_id, branch_id, customer_group_id,
   credit_limit, credit_days, status,
   created_at, modified_at, created_by, updated_by, version, is_deleted)
SELECT
  gen_random_uuid(), c.id, c.company_id, c.branch_id, c.customer_group_id,
  cg.credit_limit, cg.credit_days, c.status,
  now(), now(), 'system_backfill', 'system_backfill', 1, false
FROM customers c
LEFT JOIN customer_groups cg ON cg.id = c.customer_group_id
WHERE c.is_deleted = false;
```

### C.4 Mobile Duplicate Check Cross-Company Safety

**Evidence (VERIFIED FROM SMRITI SOURCE CODE, customer_identity.py lines 256-264):**
```python
stmt_mob = select(Customer).filter(
    or_(*mob_clauses),
    Customer.is_deleted == False,
)
if self.tenant_ctx.company_id:
    stmt_mob = stmt_mob.filter(
        (Customer.company_id == self.tenant_ctx.company_id)
        | (Customer.company_id.is_(None))
    )
```

**Finding:** Mobile duplicate check is COMPANY-SCOPED. Company A cannot see Company B
mobile matches. Safe in current state.

**Post-Model C risk:** After customers.company_id becomes nullable, the clause
(Customer.company_id.is_(None)) would match ALL tenant-scoped identity records,
potentially triggering POSSIBLE_DUPLICATE warnings across companies.
Only ExistingCustomerSummary (6 fields: id, code, name, mobile, email, gst_number, status)
is returned in a duplicate warning. Full record not exposed.

**Status: PARTIALLY VERIFIED.** Current state is safe. Post-Model C requires
deliberate RBAC review of what a cross-company duplicate warning reveals.

Rollback = DELETE inserted rows from customer_relationships. Zero schema change.

## 8. Architectural Decisions Requiring Business Approval

| # | Decision | Options | Impact |
|---|---|---|---|
| BD-1 | Customer identity scope: tenant or company? | (A) Tenant-scoped -- enables cross-outlet loyalty, returns, credit. (B) Company-scoped -- lower risk, current state. | BLOCKING for Phase 2. Not required for Phase 1. |
| BD-2 | Canonical business identity anchor? | (A) PAN number. (B) Mobile. (C) GSTIN. (D) Composite (PAN OR mobile OR GSTIN). | Affects deduplication logic and merge workflow design. |
| BD-3 | Loyalty points shared across legal entities? | (A) Tenant-level: earn at Store A, redeem at Store B. (B) Company-level: isolated (current). | Revenue and inter-company accounting impact. |
| BD-4 | Who can run cross-company customer lookup? | (A) GROUP_CFO/SYSADMIN only. (B) Any MANAGER in the tenant. (C) Blocked. | RBAC policy and data privacy. |
| BD-5 | How are cross-outlet returns settled between legal entities? | (A) Inter-company credit note (CFO sign-off). (B) Customer account credit only. (C) Cross-outlet returns blocked. | GST compliance: cross-company returns involve distinct persons per CGST Act s.25(4). |
| BD-6 | Consolidated credit exposure? | (A) Sum outstanding across all companies for same customer identity. (B) Per-company only (current). | Credit risk management and CFO policy. |
| BD-7 | Add parent_company_id to companies table? | (A) Add column for group hierarchy. (B) Use customer_relationships (current proposal). (C) Defer. | Affects financial consolidation and reporting. |
