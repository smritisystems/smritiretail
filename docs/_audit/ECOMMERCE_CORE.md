## 1. Executive Summary & Canonical Product Decision

eCommerce and Omnichannel Commerce are **FIRST-CLASS CORE CAPABILITIES** of SMRITI Retail OS.

### Canonical Principles:
1. **eCommerce is a SALES / COMMERCE CHANNEL, NOT a duplicate ERP:** Online channels (Shopify, WooCommerce, SMRITI Web Store, Marketplaces, Custom Portals) feed into the unified company-authoritative commerce engines.
2. **One Company = One Operational Database = All Channels:** Operational transactions generated by an online channel for Company 001 reside inside `smriti001`; transactions for Company 002 reside inside `smriti002`.
3. **No Shared Operational Database:** Never create a shared transactional database (`SmritiEcom`) for operational commerce state.
4. **No Duplicate Business Authorities:** eCommerce uses the existing authoritative engines for Product (`products`), Customer (`customers`), Sales (`sales_orders`, `sales_invoices`), Inventory (`stock_movements`, `products`), Tax (GST engine), and Fulfilment (`dispatches`, `packing_slips`).
5. **Inventory Authority (Ledger Principle):** Core inventory is governed by the authoritative company stock movements and stock ledger entries (`stock_movements`, `stock_ledger_entries`). `products.reserved_stock` is a **reservation state mechanism** to prevent overselling; available channel inventory is a calculated projection (`stock - reserved_stock`). Channel stores NEVER own an independent inventory ledger.

## 6. Formal Governance Sections (Rule 9)

### Evidence
- PostgreSQL 17 direct query confirmed that `control_ecom_configs` does not exist in `smritisys` (`information_schema.tables` check returned `False`).
- Source code inspection confirms `backend/app/services/ecom_reservation.py` performs atomic `SELECT ... FOR UPDATE` stock reservations and transactional outbox event emission to `ECOM_QUEUE`.
- Live forensic execution confirmed that reservation of 3 units on SKU `CH-24-G-BLACK-36` in `smriti001` resulted in **EXACTLY 0 operational writes to `smritisys`** and **0 writes to `smriti002`**.
- Test regression suites executed with **336 passed / 336 total (Exit Code: 0)**.

### Interpretation
- SMRITI Retail OS possesses the complete core transactional backend architecture (`sales_orders`, `products.reserved_stock`, `IntegrationOutboxEvent`, `CompanyDatabaseResolver`) required to operate eCommerce as a native channel.
- **Core transactional eCommerce primitives:** **`VERIFIED`**.
- **External ingress connectors:** **`NOT IMPLEMENTED / UNVERIFIED`**.
- The overall capability is correctly classified as **`Partially Verified`**.

### Recommendation
1. Maintain eCommerce as a **CORE CAPABILITY** across all canonical architecture specifications and module inventories.
2. **Future Implementation Phase:**
   - Evaluate and, if approved, implement external commerce webhook ingress for Shopify, WooCommerce, and other supported channels.
   - Any implementation must:
     - Resolve Company context first (`CompanyDatabaseResolver`)
     - Validate external platform identity
     - Enforce order and webhook idempotency
     - Write operational transactions only to the resolved Company DB (`smriti<Code>`)
     - Never write operational transactions to `smritisys`
     - Preserve physical cross-company isolation
     - Be runtime verified before documentation status changes.
3. Clean up obsolete `ECOM_DATABASE_URL` references in `backend/app/core/config.py` during the next scheduled configuration cleanup.
