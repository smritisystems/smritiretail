# SMRITI AI AGENT ARCHITECTURE & DATABASE GOVERNANCE RULES

**Status:** **PERMANENT MANDATORY DIRECTIVE — ZERO EXCEPTIONS**  
**Canonical Specification:** [`docs/architecture/MULTI_COMPANY_2.md`](file:///F:/SMRITRretailNX/docs/architecture/MULTI_COMPANY_2.md)  
**Effective Date:** 2026-08-17

All coding assistants, subagents, and automated software agents operating on the SMRITI Retail OS repository MUST strictly adhere to the following 11 non-negotiable architectural rules before proposing or applying any code or schema modifications:

---

## The 11 Golden Architecture Rules

### Rule 1: `smritisys` is strictly the Control Plane
`smritisys` stores authentication, global users, RBAC roles/permissions, company and branch registries, database routing tables (`company_database_registries`), schema governance records, immutable menus (34 items), central static masters (e.g. `smriti_banks`), and system audit logs. `smritisys` is NEVER the operational source of truth for transactional data.

### Rule 2: Company Database is the authoritative Operational Source of Truth
Every operational transactional write and read (sales invoices, purchase orders, purchase receipts, stock movements, customer balances, local inventory) MUST execute against the assigned Company Database (`smriti001`, `smriti002`, `smriti<Code>`).

### Rule 3: `tenant_id` column filtering is NOT Physical Isolation
Never attempt to replace physical database routing with SQL-level `WHERE tenant_id = ...` or `WHERE company_id = ...` queries in a shared operational database. Physical multi-tenancy is enforced at the database connection string and session level.

### Rule 4: `CompanyDatabaseResolver` is the sole Authoritative Router
All business routes and services must obtain their transactional database session via `CompanyDatabaseResolver`. Business modules and API routers MUST NEVER independently instantiate database connections or bypass resolver routing.

### Rule 5: Never create a shared operational database architecture
Do not merge company operational tables into a single database. Every registered enterprise company requires its own independent physical PostgreSQL database instance provisioned via `CompanyDatabaseProvisioner` and registered in `company_database_registries`.

### Rule 6: Never make PSV the Core Inventory Ledger
Party Stock Visibility (PSV) is a shadow projection engine for consignment, supplier visibility, and party tracking. PSV stock events (`psv_stock_events`) and balances (`psv_stock_balances`) are non-authoritative projections and MUST NEVER mutate or substitute core inventory tables (`products.stock`, `stock_movements`).

### Rule 7: Never move Master Data without an Approved Ownership Policy
Master data entities must strictly follow their classified ownership policy (`CENTRAL`, `COMPANY`, or `HYBRID`). Central products (`product_identities`) do NOT equal shared company stock; central customer profiles do NOT equal shared company credit limits or receivables.

### Rule 8: Never claim VERIFIED without Executable Evidence
Every status claim must be proven with literal terminal test outputs, `git diff` outputs, or live PostgreSQL query measurements. Never state that a feature or test is verified merely because code exists or looks complete.

### Rule 9: Never rewrite Historical Architecture Documents
Never overwrite historical audit reports, ADRs, or previous phase summaries. When documenting architectural changes, create new versioned documents or append status updates while preserving historical records with explicit `HISTORICAL` / `SUPERSEDED` banners.

### Rule 10: Never drop Operational Data without Explicit Authorization
Never execute `DROP DATABASE`, `DROP TABLE`, `TRUNCATE`, or bulk `DELETE` commands on operational tables or PostgreSQL instances without an independently verified full backup and explicit user authorization.

### Rule 11: eCommerce & Omnichannel is a Core Channel, NOT a Duplicate ERP
- **Core Capability:** eCommerce and Omnichannel Commerce are first-class core capabilities of SMRITI Retail OS, not optional plugins or detached systems.
- **Unified Commerce Flow:** eCommerce is a channel that converges on the authoritative company operational engines (`sales_orders`, `sales_invoices`, `products`, `customers`, `payments`, `dispatches`).
- **Company DB Ownership:** All operational transactions generated by online channels belong strictly to that company's operational database (`smriti<Code>`).
- **No Shared eCommerce Database:** Never create a shared operational eCommerce transaction database.
- **No Duplicate Business Authorities:** Never create duplicate Product, Customer, Sales, Tax, or Inventory master engines for eCommerce.
- **Integration Identities:** External platform identifiers (Shopify ID, WooCommerce ID, Amazon Order ID) are integration attributes attached to SMRITI master entities, not replacements for SMRITI identities.
- **Inventory Authority:** Channel inventory is an availability projection; reservations (`EcomInventoryReservationService`) atomically lock company stock. Channel stores NEVER own independent core inventory authority.
- **Webhook & Intake Idempotency:** All external commerce intakes, webhooks, and replay events must be strictly idempotent using unique causation/correlation identifiers.
